# 状态同步与帧同步

## 帧同步

**核心思想：** 服务器只转发操作（输入），不计算逻辑。客户端各自运行相同的逻辑引擎。

- **工作原理：** 所有的客户端在同一时刻执行相同的指令。服务器像一个“发令枪”，收集所有玩家的按键操作（如：向左移动、释放技能），然后定时广播给所有客户端。
- **一致性保证：** 必须保证逻辑是**确定性**的。也就是说，同样的输入，在同样的初始状态下，经过同样的计算，结果必须完全一致（这通常涉及禁用浮点数、使用定点数，以及统一随机数种子）。

**优点：**

- **流量极小：** 只传输按键信息（几个字节），与场景复杂度无关。
- **打击感强：** 适合动作游戏、格斗游戏，逻辑在本地跑，响应非常丝滑。
- **回放简单：** 记录下所有的操作指令流，就能完美重现整局游戏。

**缺点：**

- **网络要求高：** 一旦有人卡顿，所有人都要等（或通过缓存帧解决），容易出现“瞬移”。
- **反作弊难：** 逻辑都在客户端算，如果不做服务器校验，玩家很容易修改内存（如修改攻击力）。
- **断线重连慢：** 必须从第 1 帧开始追赶到当前的帧数。

> **典型案例：** 《王者荣耀》、《星际争霸》、《魔兽争霸 3》。

## 状态同步

**核心思想：** 服务器是“最高统帅”，负责所有计算；客户端只是一个“表现层”。

- **工作原理：** 客户端把操作发给服务器，服务器计算后得出结果（如：小明现在的坐标是

  $$(x, y)$$，血量剩下$$50\%$$），然后将这些**状态结果**下发给所有客户端。

- **一致性保证：** 服务器说了算。如果客户端本地预测的位置和服务器下发的不符，客户端必须强制修正（回拉）。

**优点：**

- **安全性高：** 逻辑全部在服务器，作弊难度极大。
- **断线重连快：** 连上后直接下发当前时刻的最新状态数据包即可。
- **容错性强：** 某个玩家网络抖动不影响其他人的逻辑运行。

**缺点：**

- **流量消耗大：** 随着场景内物体增多（如 100 人的吃鸡游戏），需要下发的状态信息成倍增加。
- **开发复杂度：** 为了解决延迟感，需要做大量的前端预测、插值平滑算法。

> **典型案例：** 《魔兽世界》、《和平精英》（吃鸡类）、《英雄联盟》（部分逻辑）。

## 为什么LOL是状态而农是MOBA？

**《王者荣耀》（移动端/手游）：** 手机用户在 2015 年前后主要依赖 4G 甚至 3G 网络，流量资费相对较高。**帧同步**最大的优势就是**流量极小且恒定**。无论屏幕上有多少个小兵、特效多华丽，服务器只转发玩家的按键输入。这让手游玩家在非 Wi-Fi 环境下也能流畅对局，不至于打一场球赛就耗尽流量包。

**《英雄联盟》（PC端）：** PC 玩家通常拥有稳定的光纤宽带，带宽不是首要考虑的问题。**状态同步**虽然数据包较大（需要实时下发成百上千个单位的坐标、血量、属性），但 PC 端的网络承载能力完全吃得消。

# 游戏循环

## 原始循环

```c++
while (gameRunning) {
    processInput(); // 1. 处理输入（按键、鼠标）
    update();       // 2. 更新逻辑（位置计算、AI、碰撞）
    render();       // 3. 渲染画面（交给 OpenGL 绘图）
}
```

**问题所在：** 如果你的电脑性能超强，这个循环每秒能跑 1000 次（1000 FPS）；如果我的电脑很旧，每秒只能跑 30 次（30 FPS）。

**结果：** 同样一段代码 `position.x += 1`，在你的电脑上角色跑得像闪电，在我这儿像蜗牛。这显然是不行的。

引入时间Δt：

为了让不同电脑上的位移一致，我们需要知道**“距离上一帧过去了多久”**。这个时间差通常被称为 **$\Delta t$ **。

**逻辑变为：**$$\text{新的位置} = \text{旧的位置} + \text{速度} \times \Delta t$$

这样，无论帧率高低，物体在单位时间内移动的距离都是一样的。这是目前大多数简单游戏和独立引擎的基础做法。

## 可变时间步长

游戏循环每跑完一圈，就计算一下这一圈花了多久（$\Delta t$），然后把这个时间交给逻辑层。

**工作原理**

1. 记录当前时间 $t_1$。

2. 执行游戏逻辑和渲染。

3. 记录结束时间 $t_2$，计算 $\Delta t = t_2 - t_1$。

4. 下一次循环时，所有的物理移动都乘以这个 $\Delta t$：

   $$\text{position} = \text{position} + \text{velocity} \times \Delta t$$

**优缺点**

- **优点：** 逻辑简单，能完美利用硬件性能。如果你有一张 4090 显卡，游戏能跑 300 帧，动作会看起来极其丝滑。
- **缺点（致命）：** **不确定性**。
  - **物理崩溃：** 如果某一帧因为后台扫毒突然卡了 0.2 秒，$\Delta t$ 就会变大。速度快的子弹可能会在这一帧直接跳过墙壁。
  - **数值漂移：** 由于浮点数精度问题，同一个跳跃动作，在 60 帧和 144 帧下，跳起的高度可能会有细微差别。

## 固定步长

**工作原理**

无论渲染帧率（FPS）是多少，物理更新始终以固定的频率（比如每秒 50 次，即 $\Delta t = 0.02s$）运行。

**核心算法：累加器**

为了对齐渲染和物理，引擎内部维护了一个“待处理的时间池”：

1. 每一帧开始，计算真实的耗时（现实流逝了多少时间），并丢进“时间池”。
2. 检查池子里够不够 $0.02s$？
3. **够：** 执行一次物理逻辑（FixedUpdate），从池子里扣掉 $0.02s$。
4. **循环：** 如果池子里还有时间，继续执行物理逻辑，直到剩下的时间不够 $0.02s$ 为止。
5. **渲染：** 把剩下的那一点点时间留着，等下一帧凑够了再算，直接去执行渲染。

**优缺点**

- **优点：**
  - **稳定性：** 无论电脑卡不卡，物理模拟的每一步都是 $0.02s$，不会出现“穿墙”。
  - **确定性：** 方便做**帧同步**，因为每一步的物理结果在所有设备上都是可预测的。
- **缺点：** 可能会产生“螺旋效应”。如果物理逻辑太重，导致这一帧处理不完，池子里的时间会越攒越多，导致下一帧要处理更多的物理步，最终游戏彻底卡死。

固定时间步长的一个原因是解决可变时间步长Δt的问题

**Delta Time 也有缺陷。** 如果某一帧因为系统卡顿，$\Delta t$ 突然变得很大（比如 $0.5$ 秒），而你的物体速度很快，它可能会在这一帧直接“瞬移”穿过一堵墙，导致碰撞检测失效。

**解决方案：固定步长**

我们将**逻辑更新**和**画面渲染**拆开：

1. **渲染 (Render)：** 依然是能跑多快跑多快，保证画面流畅。
2. **物理 (Physics/Update)：** 必须按照固定的频率（比如每秒精确地跳动 50 次，即每隔 $0.02s$ 计算一次）。

如果这一帧时间过长，程序会连续运行多次物理计算，把落下的进度补回来，从而保证物理模拟的稳定性。

## 游戏循环的三个阶段

### A. 捕获

这不仅仅是看你有没有按键，还包括网络消息的接收。可能还涉及到鼠标点击选块的射线检测准备。

### B. 模拟

这是游戏的“大脑”。

- 处理物体的速度、加速度。
- 检查两个方块是否重叠（碰撞）。
- 触发剧情脚本或 AI 决策。

### C. 呈现

- 清空缓冲区。
- 把模型数据传给 GPU。
- 处理光照、阴影和后处理特效。

## Unity里的循环

### Update：对应“变长步长”的渲染循环

`Update` 是每一帧（Frame）执行一次。它的执行频率是不固定的，完全取决于显卡的渲染速度和 CPU 处理当前帧的耗时。

- **执行时机：** 每一帧渲染前。
- **时间间隔：** `Time.deltaTime`（两次 `Update` 之间的时间）。
- **用途：** 接收玩家输入（如 `Input.GetKeyDown`）。
  - 非物理的逻辑更新（如计时器、UI 变化）。
  - 物体旋转、简单的位移插值。
- **特点：** 如果你的帧率从 60 掉到 30，`Update` 也会跟着变慢。

### FixedUpdate：对应“固定步长”的物理循环

`FixedUpdate` 是按照预设的固定时间间隔执行的，与帧率（FPS）无关。

- **执行时机：** 物理引擎计算前。
- **时间间隔：** `Time.fixedDeltaTime`（默认通常是 $0.02s$，即每秒固定执行 50 次）。
- **用途：** 处理所有的**物理逻辑**（如给 `Rigidbody` 加力、处理碰撞）。
- **特点：** 如果一帧的时间很长（卡顿了），Unity 可能会在这一帧里连续运行多次 `FixedUpdate` 以追上物理时间。
  - 如果一帧的时间极短，Unity 这一帧可能根本不运行 `FixedUpdate`。

# 空间分区

空间分区可以看成是从暴力法到分治法

## 种类

**网格**

这是 Minecraft 和所有体素游戏的基础。将世界切成固定大小的块（比如 $16 \times 16 \times 16$ 的立方体）。

- **工作原理：** 玩家在哪个坐标，就只计算该坐标所属 Chunk 及其相邻的几个 Chunks。
- **优点：** 实现极其简单，内存寻址非常快（直接用坐标除以 Chunk 大小）。
- **缺点：** 如果地图很大但物体很稀疏，依然会浪费很多内存来存储空的网格。

**八叉树**

如果你在做更复杂的 CAD 建模或需要精细的细节层级（LOD），八叉树是更好的选择。

- **工作原理：** 将整个 3D 空间看作一个大盒子。如果盒子里物体太多，就把它平均切成 8 个小盒子；如果小盒子里物体还多，就继续切。
- **优点：** 能够自适应物体的疏密。空旷的地方只有一个大盒子，密集的地方会有很多细密的小盒子。
- **应用：** 非常适合处理大范围、物体疏密不均的 3D 场景。

**层次包围盒BVH**

用一个简单的形状（通常是长方体，叫 **AABB 包围盒**）把复杂的物体包起来。如果射线没射中这个盒子，那它肯定没射中盒子里的物体。

- **树状结构：**
  - **根节点：** 一个巨大的盒子，装着场景里所有的东西。
  - **中间节点：** 把它拆成两个（或多个）子盒子，每个子盒子装下一半的物体。
  - **叶子节点：** 最小的盒子，里面装着真正的三角形面片或模型。

| **特性**     | **八叉树**                   | **BVH**                          |
| ------------ | ---------------------------- | -------------------------------- |
| **划分对象** | **划分空间**                 | **划分物体**                     |
| **边界位置** | 固定的、规则的（每次对半切） | 灵活的、紧贴物体的（随物体移动） |
| **重复性**   | 一个物体可能跨越多个节点     | 一个物体只属于一个叶子节点       |
| **适用场景** | 静态场景、地形、体素世界     | **动态物体**、射线追踪、物理碰撞 |

## 应用

**渲染裁剪**

- 通过空间分区，引擎可以快速判断：**“这几个 Chunk 在摄像机的视锥体之外吗？”**
- 如果是，直接丢弃，连传给 GPU 的步骤都省了。这能让你的 FPS 翻倍甚至翻十倍。

**碰撞检测**

在Voxel Engine 中，角色移动时：

- **第一步：** 通过坐标定位到所在的 Chunk。
- **第二步：** 只拿 Chunk 里角色脚下的那几个方块做数学判定。
- **结论：** 计算量从 $O(N)$ 降低到了近乎 $O(1)$。

**BVH的应用**

**射线追踪的救星**：在 OpenGL 里写射线检测（比如鼠标点选方块，或者计算光影射击命中）时，BVH 能让计算量从 $O(N)$ 降低到 $O(\log N)$。

如果没有 BVH，显卡每一帧都要计算成千上万条射线与几十万个三角形的交点，这根本跑不动。

**处理“动起来”的物体**：在静止的场景中，用网格或八叉树很爽。但如果你加入了很多飞行的子弹、跑动的怪物，这些物体的坐标一直在变。

- 八叉树需要不停地重新计算物体在哪个格子里。
- BVH 只需要微调包围盒的大小即可，对动态物体的适应性极强。

# 延迟渲染与前向渲染

## 前向渲染

对于场景中的每一个物体，显卡都会遍历所有的光源，计算光照结果，然后画到屏幕上。

其伪代码逻辑如下：

```c++
foreach (Object obj : Scene) {
    foreach (Light light : Lights) {
        CalculateLighting(obj, light); // 对每个像素运行一次片元着色器
    }
}
```

**优点：**

- **简单直接：** 容易实现。
- **支持半透明：** 处理玻璃、水等透明物体非常自然。
- **抗锯齿友好：** 硬件抗锯齿（MSAA）在这种模式下工作得最好。

**缺点：**

- **计算浪费：** 如果两个方块重叠，前向渲染会先算后面那个方块的光照，然后再算前面的。后面那个被遮挡的部分白算了（这叫 Overdraw）。
- **光源限制：** 复杂度是 $O(\text{物体数} \times \text{光源数})$。一旦光源多了，显卡会瞬间卡死。

## 延迟渲染

为了解决“光源多就卡”的问题，开发者们发明了延迟渲染。它的核心思想是：**先别算光照，先看看哪些像素是最终露出来的。**

它将渲染过程分成了两个阶段（Pass）：

1. **几何阶段：** 不计算任何光照。把物体的**颜色、法线、深度、高光**等信息，分别画到几张像图片一样的缓冲区里。这些缓冲区合在一起叫做 **G-Buffer (Geometry Buffer)**。
2. **光照阶段：** 拿着 G-Buffer。对于屏幕上的每一个像素，我只需要根据对应位置的法线和深度，算一次光照即可。

**优点：**

- **光源自由：** 光照计算只跟屏幕像素有关，跟场景里有多少物体无关。你可以放几千个光源，只要它们覆盖的像素范围合理，性能依然很稳。
- **零浪费：** 只有最终显示在屏幕上的像素才会参与光照计算，完美解决了遮挡浪费问题。

**缺点：**

- **内存压力大：** 维护 G-Buffer 需要大量的显存和带宽。
- **半透明噩梦：** 延迟渲染天生不支持半透明物体（因为 G-Buffer 每一格只能存一个深度，没法存一层玻璃后面还有一个方块）。
- **抗锯齿难：** 传统的 MSAA 无法直接在延迟渲染上使用。

| **特性**       | **前向渲染 (Forward)**              | **延迟渲染 (Deferred)**              |
| -------------- | ----------------------------------- | ------------------------------------ |
| **光源数量**   | 少量（通常 < 10 个）                | 大量（成百上千个）                   |
| **计算复杂度** | $O(\text{物体} \times \text{光源})$ | $O(\text{像素} \times \text{光源})$  |
| **半透明物体** | 完美支持                            | 极其麻烦（通常需要额外的前向渲染层） |
| **内存开销**   | 低                                  | 高 (G-Buffer)                        |
| **适用场景**   | VR、移动端游戏、简单 3D             | 3A 大作、光影复杂的现代 PC 游戏      |

**前向渲染**是“按物体画”，一个物体画完了再画下一个。

**延迟渲染**是“按像素画”，先把场景信息存成几张图，最后像处理照片滤镜一样统一打光。

# 以空间换时间的其它地方

前面的延迟渲染的G-Bufer和Shadowmap的Z-Buffer都有一种以空间换时间的思想

## 环境光遮蔽

 (SSAO - Screen Space Ambient Occlusion)

SSAO 简直就是 G-Buffer 思想的“完美搭档”。

- **做法：** 既然我们已经在 G-Buffer 里存了**深度**和**法线**，那我们就不需要再去遍历复杂的 3D 场景了。
- **逻辑：** 只要对比屏幕上相邻像素的深度值：如果某个像素被周围的像素“包围”了（深度更深），那它这里的环境光就该暗一点。
- **本质：** 直接在 2D 缓冲区上做“假 3D”计算，把原本需要光线追踪才能算的遮挡关系，变成了简单的图像处理。

## 预计算光照贴图

既然你提到了“以空间换时间”，Lightmaps 是这方面的极端代表。

- **做法：** 对于静态的方块（比如你的 Voxel 地图），光照是不会变的。那我们为什么要在运行时每帧计算呢？
- **逻辑：** 在游戏发布前，离线算好光照和阴影，然后直接“画”在物体的纹理上。
- **本质：** 用**磁盘空间（贴图文件）彻底换掉了运行时的显卡计算时间**。

## 位移贴图与法线贴图

- **做法：** 如果你想要方块表面看起来有细微的凹凸感（比如砖块的缝隙），不需要真的去建几千个细小的三角面。
- **逻辑：** 预先将表面的倾斜角度（法线信息）存进一张 RGB 图片里。渲染时，光照计算直接读取图片里的法线，让平整的表面看起来像是有高低起伏。
- **本质：** 用一张**图片的空间**，换取了**极其复杂的几何体渲染时间**。

# 预测、插值和补偿

它们的核心目的只有一个：**在存在物理延迟（Ping值）的情况下，通过数学和算法伪造出一种“实时、丝滑”的假象。**

如果没有这三者，由于网络包在传输中需要时间，你会发现你按键 100ms 后角色才动，或者看到其他玩家在屏幕上像幻灯片一样“瞬移”。

## 客户端预测

**解决的问题：** “我动，但我感觉不到延迟。”

- **工作原理：** 当你按下“向前”键，客户端**不再等待**服务器回包，而是直接在本地先修改角色的坐标。
- **数学逻辑：** 客户端先算一步 *P**l**oc**a**l*=*P**o**l**d*+*V*×Δ*t*。
- **冲突处理：** 稍后服务器的回包到了，说“你现在的坐标应该是 *P**ser**v**er*”。如果 *P**l**oc**a**l* 和 *P**ser**v**er* 差别很小，就忽略；如果差别很大（比如你撞墙了服务器没过），客户端必须强制把角色拉回到服务器的位置。

> **比喻：** 就像一个自信的下属，先按照自己的想法去办（预测），等老板（服务器）审批。如果老板没意见，就继续；如果老板说办错了，就推倒重来。

## 状态插值

**解决的问题：** “我看别人动，但不卡顿。”

- **工作原理：** 服务器通常每秒只发 10-20 次其他玩家的位置（状态同步）。如果客户端直接按这个频率画图，你看到的敌人会每秒闪现 10 次。

- **做法：** 客户端并不显示敌人“当前”的位置，而是显示敌人“过去”的位置。

- **数学公式：** 假设我们有服务器发来的 *t*1时刻位置 *P*1 和 *t*2时刻位置 *P*2。在 *t*1 到 *t*2 之间，客户端通过线性插值（Lerp）算出每一个渲染帧的中间位置：

  $$P_{render} = P_1 + (P_2 - P_1) \times \frac{t_{now} - t_1}{t_2 - t_1}$$

- **代价：** 你看到的敌人位置其实比服务器上慢了约 100ms，但这换来了极其丝滑的视觉体验。

## 延迟补偿

**解决的问题：** “我瞄准打中了，但系统说没中。”

这是射击游戏（FPS）最核心的技术。由于“状态插值”的存在，你看到敌人的位置是他在 100ms 之前的影子。如果你对着影子开火，等子弹信息传到服务器，敌人早已走远了。

- **工作原理（服务器倒带）：**
  1. 玩家 A 在本地瞄准并开火。
  2. 服务器收到“开火”指令，同时记录下玩家 A 当时的延迟（假设是 100ms）。
  3. **时空倒流：** 服务器翻开历史记录，查找 100ms 前全场所有玩家的位置。
  4. **判定：** 在那个“历史时刻”，玩家 A 的准星是否真的对准了敌人的模型？如果是，判定击中。
- **后遗症：** 这就是为什么有时候你已经跑进掩体后面了，却还是被打死了。因为在对方的屏幕里，你还没进掩体，服务器为了公平“补偿”了他的延迟。

**我动：** 靠 **预测**（本地先跑，不等回包）。

**我看别人动：** 靠 **插值**（平滑渲染过去的影子）。

**我打别人：** 靠 **补偿**（服务器帮我追溯过去）。

## 例子

在Minecraft中有这样一个机制 当玩家从高空掉落在地上的时候 如果地上有一个不死图腾 此时玩家会直接触发不死图腾而不会摔死 但换成可以被不死图腾拯救的生物却不会如此。

真相是这样的 Minecraft的单人模式其实是一个单人服务器 服务器会预判玩家行动的下一个位置 玩家摔落时 预测衰落的未来状态捡起了不死图腾 而摔死在之后 所以没被摔死 其它生物没有这种预测 所以摔死了

# 实体组件系统ECS

ECS 是一种**面向数据传输**的架构

**Entity（实体）：它只是一个 ID**

在 ECS 里，实体**不是对象**，它就是一个单纯的整数（如 `1001`）。

它就像一个“挂钩”，本身没有任何数据和逻辑。

**Component（组件）：纯数据块**

组件是**纯结构体 (Struct)**，里面只有数据，没有函数。

- `PositionComponent { float x, y, z; }`
- `VelocityComponent { float vx, vy, vz; }`
- `HealthComponent { int hp; }`

**System（系统）：纯逻辑处理**

系统负责“干活”。它不属于任何一个实体，它只关心**特定组合**的组件。

- **移动系统：** 遍历所有同时拥有 `Position` 和 `Velocity` 的实体，计算

  $$P = P + V \times \Delta t$$

- **渲染系统：** 遍历所有拥有 `Position` 和 `Mesh` 的实体，调用 OpenGL 绘图。

# MVC

**A. Model（模型）**

- **职责**：负责存储纯粹的数据和业务逻辑。它完全不知道“屏幕”的存在。
- **例子**：在你的 Voxel Engine 中，Model 存储的是：玩家的 HP、背包里的方块数量、地图的 3D 数组数据。
- **金律**：Model 不准持有任何 View 的引用。

**B. View（视图）**

- **职责**：负责把 Model 里的数据“画”出来。它只负责显示。
- **例子**：OpenGL 渲染出的血条 UI、屏幕上跳出的数字、方块的网格模型。
- **金律**：View 应该是非常“笨”的，它不该决定逻辑，只管展示。

**C. Controller（控制器）**

- **职责**：接收用户的输入（键盘、鼠标），并根据输入去修改 Model。
- **例子**：当玩家按下“拾取”键，Controller 接收到指令，告诉 Model：“给玩家背包加一个方块”。
- **金律**：它是 Model 和 View 之间的桥梁。

## 流程

**用户操作**：点击了屏幕上的“加血”按钮。

**Controller 响应**：Controller 捕获点击事件，验证逻辑（如：是否有药水？），然后调用 `Model.addHealth(20)`。

**Model 改变**：Model 里的 `hp` 变量从 80 变成了 100。

**同步 View**：

- *主动模式*：Model 发出一个“我变了”的通知（观察者模式）。
- *被动模式*：Controller 告诉 View：“Model 变了，你赶紧刷新一下”。

**View 刷新**：屏幕上的红色血条变长了。

## Unity中

在 Unity 中，找不到明显的 `Controller` 或 `Model` 类，它使用的是 **GameObject-Component** 模式。

- **View & Model 的混合体：** `MonoBehaviour` 脚本既持有数据（如 `public float speed`，像 Model），又持有逻辑（如 `Update` 里的位移，像 Controller），同时它还挂在渲染对象上（像 View）。这种做法初看很不 MVC，但开发效率极高。
- **如何实现 MVC？** 资深 Unity 开发者通常会手动实现 **MVVM** 或 **MVC**。
  - **Model**：使用纯 C# 类或 `ScriptableObject` 存储数据。
  - **View**：通过 UGUI 处理界面显示。
  - **Controller/ViewModel**：作为中介，利用 **C# 事件（Events）** 来解耦。
