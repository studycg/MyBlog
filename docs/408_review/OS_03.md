# 进程通信

进程通信指的是进程之间的信息交换，进程之间⼀般是相互独立的，但内核空间是每个进程都共享的，所以进程之间要通信必须通过内核。

## 共享存储

这是所有 IPC 方式中**最快**的。

- **原理**：操作系统拿出一块真实的物理内存，同时映射到进程 A 和进程 B 的虚拟地址空间里。
- **结果**：进程 A 往这块内存写数据，进程 B 瞬间就能看到，**完全不需要经过内核的拷贝**。

## 消息队列

既然管道是无格式的字节流（容易像 TCP 一样粘包），那就弄个有格式的。

- **原理**：操作系统在内核中维护一个**链表**。进程 A 把打包好的“消息块”扔进队列，进程 B 按规则（可以按消息类型）去取。
- **优点**：解决了格式问题，且发送方不需要一直等接收方（异步）。
- **缺点**：每次读写都要经过用户态到内核态的**拷贝**，性能有损耗。

若通信的进程之间不存在可直接访问的共享空间，则必须利用操作系统提供的消息传递方法进行进程通信，进程通过系统提供的发送消息和接收消息两个**原语**进行数据交换。

- 直接通信方式：发送进程直接把消息发送给接收进程，并将它挂在接收进程的消息缓冲队列上，接收进程从消息缓冲队列中取得消息。
- 间接通信方式：发送进程把消息发送到某个中间实体，接收进程从中间实体取得消息。这种中间实体一般称为信箱。

## 管道

管道是指用于连接一个读进程和一个写进程以实现它们之间的通信的一个**共享文件**，又名 pipe 文件，向管道（共享文件）提供输入的发送进程（写进程），以字符流形式将大量的数据送入（写）管道；而接收管道输出的接收进程（即读进程）则从管道中接收（读）数据。

- 管道传输数据是**半双工**通信，某一时刻只能单向传输。
- 写入管道中的数据遵循**先入先出**的规则
- 管道所传送的数据是无格式的，这要求管道的读出方与写入方必须事先约定好数据的格式，如多少字节算一个消息等
- 管道不是普通的文件，不属于某个文件系统，其只存在于内存中
- 管道在内存中对应一个缓冲区，不同的系统其大小不一定相同
- 从管道读数据是一次性操作，数据一旦被读走，它就从管道中被抛弃，释放空间以便写更多的数据
- 通信效率低，不适合进程间频繁地交换数据。

**匿名管道**：没有名字的管道，用完就销毁。只适用于**父子进程之间的通信**。

**命名管道**：提前创建了⼀个类型为管道的设备文件，在进程里只要使用这个设备文件，就可以相互通信，所以它可以在不相关的进程间进行通信。

### 命名管道

命名管道（FIFO）不同于匿名管道之处在于它提供了一个**路径名**与之关联，以 FIFO 的文件形式存在于文件系统中，这样，即使与 FIFO 的创建进程不存在亲缘关系的进程，只要可以访问该路径，就能够彼此通过 FIFO 相互通信，因此，通过 FIFO 不相关的进程也能交换数据。

与无名管道 (pipe) 不同之处：

1. FIFO 在文件系统中作为一个特殊的文件而存在，但 FIFO 中的内容却存放在内存中；
2. 当使用 FIFO 的进程退出后，FIFO 文件将继续保存在文件系统中以便以后使用；
3. FIFO 有名字，不相关的进程可以通过打开命名管道进行通信。

## 信号量

注意，信号量**不是用来传输具体数据的**，而是用来**实现同步互斥**的。

- **痛点**：既然“共享内存”这么快，如果进程 A 正在写数据，写了一半，进程 B 就跑去读，读到的就是错乱的数据（竞态条件）。
- **配合**：所以**信号量通常和共享内存搭配使用**，作为一个“锁”，保证同一时刻只有一个进程能操作那块内存。

**P(wait)操作**：将信号量-1，若相减后信号量<0那么表示资源已被占用，进程需阻塞等待。若相减后>=0那么表示还有资源，进程可以正常执行。

**V(singal)操作**：将信号量+1，相加后若信号量<=0则标明当前有阻塞中的进程，于是会将该进程唤醒运行。如果相加后信号量>0，则表明没有阻塞中的进程。

## 套接字

之前复习网络时聊过的 Socket。

- **原理**：不仅可以跨网络和不同电脑通信，也能在**同一台电脑的不同进程间**通信（如 Unix Domain Socket）。
- **优点**：极其灵活，客户端和服务器开发通用。
- **缺点**：开销最大（要走一遍网络协议栈的流程）。

## 为什么共享内存比管道/消息队列快？

**管道/消息队列**：需要经过 **4 次**数据拷贝。（发送方将数据从用户态拷到内核态 $\rightarrow$ 内核态存起来 $\rightarrow$ 接收方请求读取 $\rightarrow$ 从内核态拷回接收方的用户态）。

**共享内存**：只需要 **0 次**额外拷贝（或说 2 次直接内存访问）。因为物理内存是同一块，大家直接用指针在自己的用户态读写即可，直接绕过了内核的搬运过程。

## 存储映射Memory Mapping

存储映射 I/O (Memory-mapped I/O) 使一个磁盘文件与存储空间中的一个缓冲区相映射。

传统的读写文件（`read` / `write`）： 每次你需要数据，都要向操作系统申请（系统调用），操作系统把硬盘里的数据先拷到内核的**内核缓冲区**里，然后再复制到你进程的**用户缓冲区**里。这里经历了**两次拷贝**和**两次状态切换**。

**存储映射（`mmap`）** 则很直接： **它跳过了常规的读写操作，直接把磁盘上的文件，映射到你进程的虚拟地址空间**中。

- **结果**：文件里的数据仿佛变成了一个巨大的 C++ 数组。你只需要操作指针（比如 `char* ptr`），就能直接读写文件。

- 于是当从缓冲区中取数据，就相当于读文件中的相应字节。于此类似，将数据存入缓冲区，则相应的字节就自动写入文件。

- 这样，就可在不适用 read 和 write 函数的情况下，使用地址（指针）完成 I/O 操作，进程就可以直接通过读写内存来操作文件。

共享内存可以说是最有用的进程间通信方式，也是最快的 IPC 形式，因为进程可以直接读写内存，而不需要任何数据的拷贝。

| **特性**                    | **带来的优势**                                               | **对比传统 I/O**                      |
| --------------------------- | ------------------------------------------------------------ | ------------------------------------- |
| **零拷贝 (Zero-Copy) 思想** | 数据直接从磁盘加载到物理内存（这块内存同时被映射给内核和用户态），**省去了从内核态拷贝到用户态的开销**。 | 传统 I/O 需要多一次 CPU 拷贝。        |
| **减少系统调用**            | 映射建立后，读写就像访问数组一样，不需要频繁调用 `read()`/`write()`，避免了频繁在用户态和内核态之间横跳。 | 传统 I/O 每次读写都要切内核态。       |
| **跨进程共享**              | 如果两个进程映射了同一个文件，它们就在共享同一块物理内存。这就是**共享内存 IPC** 的底层原理。 | 传统 IPC 很难做到如此高效的数据共享。 |

| --------------------------- | ------------------------------------------------------------ | ------------------------------------- |

**但是存储映射也有缺点：**

- **缺页中断带来的微小卡顿**：虽然 `mmap` 不用系统调用，但触发缺页中断时，如果是从硬盘读数据，会阻塞当前线程。如果在游戏主线程（渲染线程）发生，会导致**突然掉帧**。
- **文件大小不灵活**：映射建立后，想改变文件大小比较麻烦，不适合那种需要不断追加写入的日志文件。

## 匿名映射

**普通映射**：虚拟内存 $\rightarrow$ 磁盘文件。

**匿名映射**：虚拟内存 $\rightarrow$ 物理内存（初始化为全 0）。

在调用 `mmap` 时，通过指定 `MAP_ANONYMOUS` 标志位，并把文件描述符（fd）设为 `-1`，就可以创建一个匿名映射区。

两个用途：

**代替 `malloc` 分配大块内存**：

这是 C++ 程序员最应该知道的。

- 当你调用 `malloc` 申请小内存（比如 < 128KB）时，C 运行库通常用 `brk()` 移动堆顶指针。
- 当你申请**大块内存**（比如几百 MB）时，`malloc` 底层就会调用 `mmap` 创建一个**匿名映射区**。
- **优势**：当这块内存被 `free` 时，`mmap` 占据的虚拟地址空间可以直接还给操作系统，而 `brk` 必须从堆顶向下缩减，容易产生内存碎片。

**父子进程间的通信 (IPC)**

虽然叫“匿名”，但它支持 **共享 (MAP_SHARED)**。

- 如果父进程创建了一个 **共享的匿名映射区**，然后调用 `fork()` 产生子进程。
- 由于子进程继承了父进程的页表，父子进程就会看到**同一块物理内存**。
- **优点**：不需要建立任何真实文件，就能在有血缘关系的进程间实现极速的数据共享。

| **特性**       | **普通堆内存 (brk)**                | **匿名映射 (mmap)**                                |
| -------------- | ----------------------------------- | -------------------------------------------------- |
| **分配单位**   | 字节级，灵活但易碎。                | **页级 (通常 4KB)**，适合大块数据。                |
| **释放行为**   | 不一定立即还给 OS（受内存池管理）。 | `munmap` 后立即归还虚址给 OS。                     |
| **共享性**     | 进程私有，难以直接共享。            | 可以通过 `fork` 轻松实现**进程间共享**。           |
| **内存初始化** | 需手动清零（或使用 calloc）。       | 操作系统保证映射初始时**全为 0**（出于安全考虑）。 |

# 线程通信

线程间的通信目的主要是用于线程同步。所以线程没有像进程通信中的用于数据交换的通信机制。

同一进程的不同线程共享同一份内存区域，所以线程之间可以方便、快速地共享信息。只需要将数据复制到共享（全局或堆）变量中即可。但是需要避免出现多个线程试图同时修改同一份信息。

## 分离状态

**非分离状态**：

线程的默认属性是非分离状态，这种情况下，原有的线程等待创建的线程结束。只有当 `pthread_join ()` 函数返回时，创建的线程才算终止，才能释放自己占用的系统资源。

**分离状态**：

分离线程没有被其他的线程所等待，自己运行结束了，线程也就终止了，马上释放系统资源。应该根据自己的需要，选择适当的分离状态。

## 为什么进程切换慢于线程

涉及到虚拟内存的问题，进程切换涉及虚拟地址空间的切换而线程不会。

因为每个进程都有自己的虚拟地址空间，而线程是共享所在进程的虚拟地址空间的，所以同一个进程中的线程进行线程切换时不涉及虚拟地址空间的转换。

把虚拟地址转换为物理地址需要查找页表，页表查找是一个很慢的过程（至少访问 2 次内存），因此通常使用 Cache 来缓存常用的地址映射，这样可以加速页表查找，这个 cache 就是 TLB（快表）。

由于每个进程都有自己的虚拟地址空间，那么显然每个进程都有自己的页表，那么当进程切换后页表也要进行切换，页表切换后 TLB 就失效了，cache 失效导致命中率降低，那么虚拟地址转换为物理地址就会变慢，表现出来的就是程序运行会变慢，而线程切换则不会导致 TLB 失效，因为线程线程无需切换地址空间，这也就是进程切换要比同进程下线程切换慢的原因。

# 其它进程

## 守护进程

这是游戏服务器或后台服务最常用的形态。

**定义**：在后台运行，不受终端控制，生命周期很长的进程。通常在系统启动时开始，系统关闭时结束。

**特征**：

1. **脱离终端**：没有控制终端（TTY 为 `?`），你关掉命令行窗口它也不会断。
2. **在后台运行**。
3. **名称习惯**：通常以 `d` 结尾（如 `httpd`, `sshd`, `mysqld`）。

**如何创建（面试常考点）**：

1. `fork()` 出子进程，父进程退出（为了让进程进入后台）。
2. 调用 `setsid()` 创建新会话（彻底脱离旧终端的控制）。
3. 改变工作目录到根目录 `/`（防止挂载点无法卸载）。
4. 重设文件掩码 `umask(0)`。
5. 关闭文件描述符 0, 1, 2（输入、输出、错误流）。

## 僵尸进程

**定义**：一个进程已经结束了（执行完了 `exit`），但它的父进程还没有调用 `wait()` 或 `waitpid()` 来获取它的退出状态，这个子进程就会变成僵尸进程。

**状态**：在 `ps` 命令中显示为 `Z` (Zombie) 或 `<defunct>`。

**代价**：它不占用内存或 CPU，但它占用了**进程 ID (PID)**。由于系统的 PID 资源是有限的，如果产生大量僵尸进程，会导致系统无法创建新进程。

**解决方案**：父进程必须“收尸”（调用 `wait`）；如果父进程不管，可以杀掉父进程，让僵尸进程变成孤儿进程，由 `init` 进程统一处理。

## 孤儿进程

**定义**：父进程退出了，但子进程还在运行。

**处理**：这些进程会被 **init 进程**（PID 为 1）自动领养。

**状态**：这是正常现象。init 进程会负责在它们结束时进行收尸，所以孤儿进程**不会**变成僵尸进程。
