# 同步互斥

## 互斥锁

**特性**：最常用的锁。如果锁被占用，尝试获取锁的线程会进入**休眠状态**（挂起），放弃 CPU。

**优点**：不占用 CPU 资源。

**缺点**：存在**上下文切换**开销（用户态切换到内核态，再切换回来）。如果锁定时间极短，切换开销可能比等待时间还长。

互斥锁有加锁和解锁两种状态：

- 在访问共享资源后临界区域前，对互斥锁进行加锁。

- 在访问完成后释放互斥锁导上的锁。

- 对互斥锁进行加锁后，任何其他试图再次对互斥锁加锁的线程将会被阻塞，直到锁被释放。

## 自旋锁

**特性**：如果锁被占用，线程不睡觉，而是**原地转圈（死循环）**，一直盯着锁看它什么时候释放。

**优点**：没有上下文切换，反应极快。

**缺点**：如果长时间拿不到锁，会白白**浪费 CPU**。

**场景**：适用于内核态或锁定时间极短的情况。

## 读写锁

根据访问目的，把线程分成了**读者（Reader）和写者（Writer）**，规则如下：

- **读-读 兼容**：多个线程可以**同时读取**。因为读取不会改变数据，大家一起看是安全的。
- **读-写 互斥**：有人在读时，写者必须等；有人在写时，读者必须等。
- **写-写 互斥**：同一时刻只能有一个人写。

**逻辑**：**“多读单写”**。多个线程可以同时读，但写的时候必须独占。

**场景**：游戏中的配置表、静态资源，通常读多写少，用读写锁能极大提高并发性能。

**如果一直有新的读者进来，写者会发生什么？”**

这就是读写锁的一个经典问题：**写者饥饿。

- **现象**：如果读请求源源不断，读锁可能永远不会降为 0，导致尝试加写锁的线程被无限期阻塞。
- **解决方案**：现代的读写锁实现通常会有**“写优先”模式**。一旦有写者在排队，后续进来的读者就不能再加锁了，必须等写者处理完。

# 死锁

## 死锁的四个条件

**互斥条件**：资源是独占的。一个资源一次只能被一个线程使用。

**请求与保持条件：线程已经拿到了一个资源，又去请求另一个资源，但在请求不到时，依然死死拽着手里的资源不放。

**不可剥夺条件**：线程持有的资源在未完成前，不能被其他线程强行抢走。

**循环等待条件**：发生了一连串的互相等待。比如：A 等 B，B 等 C，C 又在等 A。

## 死锁预防

通过限制规则来破坏死锁的四个必要条件

**破坏互斥条件**

比如假脱机技术

**破坏“循环等待”：固定加锁顺序**

这是最常用的方案。规定所有线程必须按照 **A $\rightarrow$ B** 的顺序加锁。

- 如果 T2 也先去拿锁 A，它会被阻塞在第一步，也就不会发生“拿着 B 等 A”的情况。

**破坏“请求与保持”：一次性加锁**

使用类似 `std::lock(mutex1, mutex2)` (C++11) 的方法。它会尝试同时锁定多个互斥量，如果其中一个拿不到，就会释放已经拿到的，避免“占着茅坑不拉屎”。

**破坏“不可剥夺”：使用 `try_lock`**

不要死等。如果 `try_lock` 失败，线程可以选择先释放自己手里的锁，过一会儿再重试。

## 死锁避免

不限制你加锁的顺序，而是在**资源分配时进行动态评估**。如果发现分给你资源后，系统可能会进入“不安全状态”，就拒绝你的请求。

### 安全/不安全状态

死锁避免的核心思想是：**永远不要让系统进入“不安全状态”**。

- **安全状态**：指系统能找到一种进程执行序列（$P_1, P_2, \dots, P_n$），使得每个进程都能顺利拿到所需的资源并完成任务。这个序列被称为**安全序列**。
- **不安全状态**：系统无法找到这样一个安全序列。**注意：不安全状态并不等于死锁，但它是死锁的前兆。** 只要进入了不安全状态，死锁就“可能”发生。

### 银行家算法

这个算法的名字来源于银行贷款：银行不能把所有的钱都贷出去，必须留一部分，以确保至少能让一个客户完成周转并还款，从而带动后续客户。

**核心数据结构**

在面试中，你只需要记住银行家算法维护的四个矩阵/向量：

1. **最大需求 (Max)**：每个进程总共需要多少资源。
2. **已分配 (Allocation)**：现在已经分给每个进程多少资源。
3. **还需要 (Need)**：$Need = Max - Allocation$。
4. **可用资源 (Available)**：系统现在手里还剩多少资源。

**算法逻辑**

当一个进程提出资源申请时：

1. **预分配**：系统假设把资源分给它，修改 `Available` 和 `Allocation`。
2. **安全性检查**：系统开始推演——“如果我把剩下的资源给某个进程，它能跑完吗？”
   - 如果能，就假设它跑完了，回收它占用的所有资源，再去试下一个进程。
3. **结果**：如果能为所有进程找到一个排队完成的顺序，说明是**安全**的，正式分配资源；否则，拒绝请求，让进程等待。

| **维度**       | **死锁预防 (Prevention)**                | **死锁避免 (Avoidance)**                   |
| -------------- | ---------------------------------------- | ------------------------------------------ |
| **策略**       | 静态规则，破坏必要条件。                 | 动态评估，绕开不安全状态。                 |
| **限制性**     | 很强（比如强制要求 A 锁必须在 B 锁前）。 | 较弱（允许灵活申请）。                     |
| **资源利用率** | 较低（有些资源明明空着却不给用）。       | **较高**（尽可能满足请求）。               |
| **开销**       | 低（代码写死逻辑即可）。                 | **高**（每次分配资源都要跑一遍算法推演）。 |

# 信号量

互斥锁：每次只能进入一个

信号量：可以控制个数

**一个整型计数器（S）**：表示当前可用的资源数量。

**一个等待队列**：记录着所有因为拿不到资源而被阻塞挂起的线程。

## P操作和V操作

**P 操作（Wait / Down / 申请资源）**

当你想要消耗一个资源时，执行 P 操作：

1. 计数器 `S--`。
2. 如果减完之后 `S < 0`，说明资源已经被抢光了。此时当前线程必须**阻塞睡觉**，并把自己加入等待队列中。
3. 如果减完之后 `S >= 0`，说明还有资源，线程继续执行。

**V 操作（Signal / Up / 释放资源）**

当你用完资源，或者生产出了一个新资源时，执行 V 操作：

1. 计数器 `S++`。
2. 如果加完之后 `S <= 0`，说明此时等待队列里还有人在排队。此时操作系统会从队列里**唤醒一个线程**，让它拿到资源继续跑。
3. 如果加完之后 `S > 0`，说明没人排队，资源充裕，线程继续执行。

## 实现互斥

**做法**：把信号量初始值设为 `S = 1`（这叫**二值信号量**）。

**逻辑**：进入临界区前 `P(S)`，出了临界区 `V(S)`。它的效果和 Mutex 一模一样。

## 实现同步

**做法**：把信号量初始值设为 `S = 0`。

**逻辑**：假设我们要确保“代码 A 执行完，才能执行代码 B”。

- 线程 2 执行代码 B 之前，先调用 `P(S)`。因为 `S=0`，一减变 `-1`，线程 2 立刻被挂起。
- 线程 1 执行完代码 A 后，调用 `V(S)`。`S` 变成 `0`，系统立刻唤醒线程 2。

## 资源池/限流

- **做法**：把信号量初始值设为 `S = N`（比如 N=5）。
- **逻辑**：用于限制同时访问某个资源的最大线程数。比如我们限制游戏客户端同时最多只能发起 5 个 HTTP 下载请求，防止把网络带宽挤爆。

# 条件变量

这个参考C++中的条件变量

**必须配合互斥锁（Mutex）**一起使用，专门用来处理那种“**等待某个特定逻辑条件成立**”的场景。

条件变量允许一个或多个线程在某个特定的条件（例如：队列不为空、资源已加载完成）成立之前，处于**挂起（休眠）状态。当另一个线程使该条件成立时，它可以通知（唤醒）**正在等待的线程。

- **Wait**：把自己挂起，并**释放**手里的互斥锁。
- **Notify_one / Signal**：唤醒一个正在等待的线程。 
- **Notify_all / Broadcast**：唤醒所有正在等待的线程。

| **维度**         | **信号量 (Semaphore)**                                       | **条件变量 (Condition Variable)**                            |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **是否有“状态”** | **有（计数器）**。它记录了资源的数量。如果你先释放（V操作）再申请（P操作），P操作依然能成功。 | **无（瞬时信号）**。它不保存信号。如果你先发通知再等待，**这个通知会丢失**，等待的线程将永远睡死过去。 |
| **配合工具**     | 独立使用。                                                   | **必须配合 Mutex 使用**。Mutex 用来保护那个“条件”不被并发修改。 |
| **适用场景**     | 侧重于**资源计数**和**限流**（如：线程池里有多少空位）。     | 侧重于**复杂逻辑条件的成立**（如：资源是否全部加载完毕、特定 UI 是否已关闭）。 |
| **释放权限**     | 任何线程都可以执行 V 操作。                                  | 通常由改变条件的那个线程执行 Notify。                        |

## 条件变量为什么必须使用Mutex

**原因：为了防止“错失信号”。**

如果没有锁保护：

1. 线程 A 检查条件发现不成立，准备去调用 `wait`。

2. 就在这时，操作系统切换到了线程 B。

3. 线程 B 改变了条件，并发出了 `notify`。

4. 此时线程 A 还没进入 `wait` 状态，所以这个 `notify` 被 A 漏掉了。

5. 随后线程 A 进入 `wait`。由于没有新的 `notify`，A 就会永远睡下去。

**有了 Mutex 后：** `wait` 操作会自动执行“解锁 + 挂起”的**原子操作**，确保在挂起之前不会有其他线程能修改条件。

```c++
// 消费者：工作线程
{
    std::unique_lock<std::mutex> lock(queue_mutex);
    // 关键点：防止“虚假唤醒”，必须用 while 循环检查条件
    cv.wait(lock, []{ return !task_queue.empty(); });
    // 拿到任务，处理逻辑...
}

// 生产者：主线程
{
    std::lock_guard<std::mutex> lock(queue_mutex);
    task_queue.push(new_task);
    cv.notify_one(); // 广播信号
}
```

如果你只是需要一个**简单的计数器**来管理资源（比如限制 5 个下载线程），选 **信号量**。

如果你需要线程在某个**复杂的布尔表达式**（如 `a && b || c`）为真时才运行，选 **条件变量**。
