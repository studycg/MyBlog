| **阶段**   | **输入文件**    | **处理工具**     | **输出文件（中间件）**            | **核心任务**                  |
| ---------- | --------------- | ---------------- | --------------------------------- | ----------------------------- |
| **源文件** | `.cpp`, `.h`    | —                | —                                 | 编写逻辑                      |
| **预处理** | `.cpp`          | `cpp` (预处理器) | **`.i` (翻译单元)**               | 宏展开、头文件包含、删注释    |
| **编译**   | `.i`            | `cc1` (编译器)   | **`.s` (汇编代码)**               | 语法分析、AST、优化、生成汇编 |
| **汇编**   | `.s`            | `as` (汇编器)    | **`.o` / `.obj` (目标文件)**      | 翻译为机器码、生成符号表      |
| **链接**   | `.o`, `.a/.lib` | `ld` (链接器)    | **`.exe` / `a.out` (可执行文件)** | 符号解析、地址重定位、合并节  |

`.i` 文件

- **本质**：纯文本。
- **特点**：它是源文件的“完全体”，包含了所有头文件的内容。如果你想排查某个宏为什么没生效，或者头文件是不是包含错了，看它最直接。

`.s` 文件

- **本质**：文本形式的指令。
- **特点**：它是跨越“高级语言”到“机器指令”的桥梁。在这里你能看到虚函数调用是如何变成“间接跳转”的，也能看到 `inline` 函数是否真的被展开了。

`.o` / `.obj` 文件

- **本质**：二进制机器码，但“残缺”。
- **特点**：它是不可执行的，因为它内部的外部函数地址（如 `printf`）全是 `00 00`。它还带有一张**符号表**，等着链接器来认领。

可执行文件

- **本质**：二进制机器码，且“逻辑闭环”。
- **特点**：链接器已经填平了所有的地址坑位。它通常采用 **ELF** (Linux) 或 **PE** (Windows) 格式，包含了操作系统加载程序所需的全部元数据。

# 预处理

预处理阶段就是文本处理，预处理器并不理解 C++ 语法。

**删除注释**：所有的 `//` 和 `/* ... */` 都会被替换为一个空格。

**文件包含 (`#include`)**：递归地将目标文件的内容原封不动地搬过来。

**宏展开 (`#define`)**：进行符号替换。

**条件编译处理 (`#if`, `#ifdef`)**：根据宏定义情况，决定哪些代码块进入编译器，哪些被永久丢弃。

面试官常问：**`#include <file>` 和 `#include "file"` 有什么区别？**

- **`<file>` (尖括号)**：编译器去**标准库路径**（系统路径）寻找。比如 `/usr/include`。
- **`"file"` (双引号)**：编译器先在**当前源文件所在目录**寻找。如果找不到，再退化到系统路径寻找。
- **架构影响**：如果你在大型工程中乱用双引号包含标准库，会增加搜索时间。

绝对不要在头文件中定义非内联函数或非 `const` 全局变量。因为一旦该头文件被多个 `.cpp` 包含，预处理后每个 `.cpp` 都会有一份该函数的代码，链接时必报“重定义”错误。

在现代 C++ 中，我们提倡“去宏化”。

- 用 `const` 或 `constexpr` 替代数值宏。
- 用 `inline` 函数或 `template` 替代带参数的宏。
- **唯一不可替代的场景**：条件编译（如跨平台适配、调试开关）。

条件编译用于跨平台开发

```c++
#ifdef _WIN32
    // Windows 特有 API
#elif __linux__
    // Linux 特有 API
#endif
```

防止重复包含

```c++
#ifndef MY_HEADER_H
#define MY_HEADER_H
// 头文件内容
#endif
```

现代编译器支持 `#pragma once`，它更简洁且性能略好，但 `#ifndef` 兼容性最强。

# 编译

## 编译过程

编译器处理翻译单元时，逻辑上分为三个核心步骤：

**一、词法与语法分析：构建 AST（抽象语法树）**

编译器先打碎你的代码，识别出 `if`、`int`、变量名、操作符等。

- **AST**：这是面试中常被提及的概念。编译器会将代码转换成一棵树。
- **举例**：`a = b + 3;` 会被解析成一个以 `=` 为根节点，左子树是 `a`，右子树是 `+`（其下又是 `b` 和 `3`）的树状结构。

**二、语义分析**

这是 C++ 编译器最痛苦的一步，也是最体现 C++ 语言特性的地方。

- **类型检查**：你是不是把一个 `std::string` 赋值给了 `int`？
- **作用域检查**：你调用的 `my_func()` 在当前翻译单元（或头文件声明中）存在吗？
- **符号绑定**：确定每个变量名对应内存中的哪个逻辑条目。

**三、中间代码生成与优化**

编译器不会直接跳到汇编，而是先生成一种**中间表示（IR，如 LLVM IR）**。

- **为什么？** 因为优化在 IR 上做最方便。
- **优化做了什么？** 比如“常量折叠”（把 `2 + 3` 直接变成 `5`）、“死代码消除”（永远执行不到的 `if` 块直接删掉）、“函数内联”（把函数体直接搬过来减少调用开销）。

## 编译期其它重要的事

**虚函数表的生成 **

编译器在发现类中有 `virtual` 函数时，会在**编译阶段**为这个类偷偷生成一个隐形的数组—— **虚函数表**。

- 它还会为每个对象实例插入一个隐形的指针 `vptr`。
- **注意**：表是编译时生成的，但具体跳到哪个函数是运行时决定的。

**模板实例化**

- 编译器看到 `vector<int>` 和 `vector<double>` 时，会根据模板“图纸”**手动生成两份不同的类代码**。

**名字（Name Mangling）粉碎/修饰**

`void print(int)` 可能会变成 `_Z5printi`。

`void print(double)` 可能会变成 `_Z5printd`。

这就是为什么 C 语言调用 C++ 库需要 `extern "C"`——它告诉 C++ 编译器：“别改名字，就按 C 的原始名字生成符号！”

**自动类型推导**

**`auto` 的推导**：编译器会查看初始化表达式的类型，并在 AST（抽象语法树）中把 `auto` 替换为真实的类型。

**`decltype` 的计算**：编译器会查询符号表，计算出表达式的类型，而**完全不会运行**该表达式。

**架构意义**：这保证了 C++ 的**静态类型安全**。虽然代码写起来像动态语言，但编译后的二进制代码中，所有变量的类型和偏移量都是硬编码好的，没有任何运行时开销。

**常量表达式的计算**

如果你定义了一个 `constexpr` 函数，编译器会尝试在编译时直接算出它的结果。

```c++
constexpr int factorial(int n) { return n <= 1 ? 1 : n * factorial(n - 1); }
int arr[factorial(5)]; // 编译器直接算出 120，并分配栈空间
```

`constexpr` 和 `const` 的区别？

- `const` 只是承诺“不修改”，它的值可能在运行时才确定（如读取用户输入）。
- `constexpr` 强制要求在**编译时**必须能算出结果。

**try-catch**

C++ 的异常处理（`try-catch`）并不是免费的。为了支持它，编译器在编译阶段需要生成大量的**辅助数据结构**。

**栈回溯表**：编译器会记录每个函数在执行到哪一行时，哪些局部对象已经构造好了。

**发生异常时**：程序会查阅编译阶段生成的这张表，按照构造的相反顺序一个个调用析构函数。

**架构权衡**：在嵌入式或游戏开发等极高性能要求的场景，有时会通过编译器参数（如 `-fno-exceptions`）禁用它，以减小二进制体积并提升性能。

**内存布局的确定**

编译器在编译阶段需要决定一个 `class` 或 `struct` 到底占用多少字节。

- **内存对齐 (Alignment)**：编译器会根据硬件要求（通常是 4 或 8 字节对齐），在你的成员变量之间插入“填充字节（Padding）”。
- **偏移量硬编码**：当你访问 `obj.member` 时，编译器在生成的汇编代码中，已经将其转换成了 `[obj的首地址 + 偏移量]`。这意味着在程序运行时，**“成员变量名”这个东西已经不存在了**。

**符号的可见性与内联处理**

**内联替换**：编译器会评估函数的大小和调用频率。如果觉得合适，它会将函数调用直接替换为函数体。这消除了函数调用的开销（压栈、跳转、返回）。

**静态变量初始化**：对于局部 `static` 变量，编译器会生成一段特殊的代码和标志位，确保它只被初始化一次（多线程安全通常由编译器在编译时插入锁或原子操作来保证）。

## 编译很慢

为什么编译很慢呢？

**头文件膨胀**：如果一个翻译单元包含了太多的模板（如 `<iostream>`、`<algorithm>`），编译器在构建 AST 时会消耗海量内存。

**优化级别 (`-O0` vs `-O3`)**：优化等级越高，编译器在第 ③ 步进行的逻辑推演就越复杂，编译时间呈指数级增长。

# 汇编

汇编只是机械的把汇编语言翻译成01机器码

**指令对应**：每一条汇编指令（如 `mov`, `add`, `push`）都直接对应一组机器码（二进制）。

**产物**：生成 **可重定位目标文件 (Relocatable Object File)**，即 `.o` (Linux) 或 `.obj` (Windows)。

# 链接

链接器的核心任务只有两个：**符号解析**和**重定位**。

**第一步：符号解析**

链接器会扫描所有输入的 `.o` 文件和库文件（`.a` / `.lib`），查看它们的符号表。

- **匹配过程**：它会把每个翻译单元中的“未定义符号”与另一个单元中的“已定义符号”关联起来。
- **强/弱符号处理**：
  - 如果你在两个 `.cpp` 里都定义了 `int g_val = 1;`（强符号），链接器会报错：`multiple definition`。
  - 如果你在头文件里写了 `inline` 函数，链接器会看到多个同名定义，但它知道这是 `inline`，所以会**随机选一个**，并把其他的丢弃，从而避免冲突。

**第二步：重定位**

汇编器生成的 `.o` 文件里，所有涉及外部跳转的地址都是 **0** 或者 **相对偏移量的占位符**。

**合并节**：链接器把所有 `.o` 的 `.text` 段合并成一个大的 `.text` 段，`.data` 段同理。此时，每个函数的**最终虚拟内存地址**就确定了。

**填坑：链接器回头去找那些“重定位表”里的记录。

- 汇编器笔记：“在 `main` 函数偏移 0x20 处，调用了 `foo`，地址还没定。”
- 链接器操作：既然现在已经知道 `foo` 在内存中的确切地址（比如 `0x401000`），链接器就直接修改机器码，把原本的 `00 00 00 00` 替换成 `0x401000`。

# 静态链接和动态链接

**静态链接**

- **过程**：链接器把库文件（`.a` / `.lib`）中你用到的那部分代码，直接**拷贝**到你的可执行文件中。
- **优点**：运行快，不依赖外部环境（即“带上干粮上路”）。
- **缺点**：浪费空间。如果 10 个程序都用了同一个静态库，磁盘和内存里就有 10 份重复代码。

**动态链接**

- **过程**：链接阶段只在可执行文件中记下一笔：“我用到了 `libc.so` 里的 `printf`”。真正的链接发生在**程序启动时**（由动态链接器 `ld-linux.so` 完成）。
- **优点**：节省内存（多进程共享一份库代码），更新库不需要重新编译程序。
- **缺点**：启动略慢，可能出现“DLL Hell”（版本不匹配导致程序崩了）。

## 举个例子

静态链接的10个程序都用了一个静态库 那么磁盘和内存中就有10份代码 这10个程序的意思是 最终是一个exe呢还是10个呢？

简单直接的回答是：**这指的是 10 个独立的 `.exe` 文件（或同一个 `.exe` 的 10 个运行实例）。**

假设你写了 10 个不同的工具程序（比如 `A.exe`, `B.exe` ... `J.exe`），它们都用到了一个名为 `Graphics.lib` 的静态库。

- **链接发生时**：链接器会把 `Graphics.lib` 里的机器指令分别“焊”进这 10 个 `.exe` 文件中。
- **结果**：在你的硬盘上，这 10 个文件每一个都包含了 `Graphics` 库的完整副本。
- **代价**：如果这个库有 10MB，那么你的硬盘就被占据了 $10 \times 10 = 100$ MB 的空间。这被称为**磁盘冗余**。

当你把这 10 个程序都双击运行起来时：

**加载过程**：操作系统会为每个程序创建一个独立的进程，并把它们的 `.exe` 内容从磁盘加载到各自的**虚拟地址空间**中。

**物理内存状态**：

- 由于是静态链接，每个进程的**代码段里都有一份 `Graphics` 库的代码。
- 操作系统通常无法识别出这些散落在不同进程里的代码其实是一样的。

**结果**：在你的物理内存（RAM）里，同样的 `Graphics` 指令被存储了 10 遍。

**代价**：这极大地浪费了内存资源。如果库很大，运行多个程序会导致系统内存迅速耗尽。

如果是动态链接呢？

**磁盘上**：只有 1 份 `Graphics.dll` 文件。那 10 个 `.exe` 只是记录了一个“快捷方式”。

**内存中**：操作系统非常聪明。当第一个程序启动时，它把 `Graphics.dll` 加载到物理内存。当后面 9 个程序启动时，操作系统发现这个库已经在内存里了，于是直接让这 9 个进程的虚拟地址都**指向同一块物理内存**。

**结论**：无论运行多少个程序，内存里永远只有 **1 份** 代码副本。

## 静态链接是编译时定死的

在 `.o` 目标文件中，函数调用（如 `call foo`）的地址通常是 `00 00 00 00`。

- **链接时操作**：链接器计算出 `foo` 函数在最终大文件里的**绝对虚拟内存地址**（例如 `0x401050`）。
- **定死过程**：链接器直接修改机器码，把 `0x401050` 填入跳转指令中。
- **后果**：这个地址被硬生生地写进了二进制文件。程序运行时，CPU 执行到这一行会直接跳到那个固定的内存位置，不需要任何查找过程。

因为是“定死”的，静态链接表现出极强的独立性，但也带来了“僵硬”：

- **无法共享**：如果系统里有 10 个程序都静态链接了同一个 `Graphics.lib`，那么内存里就会有 10 份一模一样的 `Graphics` 代码副本。它们互相不知道对方的存在。
- **更新即重连**：如果库文件修复了一个 Bug，你光替换库文件没用。你必须**重新运行链接器**，让它把旧的代码“挖”出来，把新的代码重新“焊”进去，生成一个新的可执行文件。

**为什么动态链接不是“死”的？**

- **动态链接**：可执行文件里只留了一个“名字”（如 `libmath.so`）。
- **活扣**：程序启动时，操作系统才去硬盘上找这个文件。如果找到了，就把它加载到内存里，然后临时把地址勾连起来。

## 地址无关代码PIC

**动态库在内存中只有一份，但每个进程加载它的地址可能不同，它是怎么做到的？”**

- **问题所在**：静态链接是在编译时**定死**地址的。但动态库（`.so`/`.dll`）被多个程序共享，它不能假设自己每次都加载到内存的同一个位置。
- **解决方案**：**PIC (Position Independent Code)**。
  - 编译器在编译动态库时（使用 `-fPIC` 参数），不直接在指令里写死全局变量和函数的地址。
  - 它引入了一个中间层：**GOT (Global Offset Table, 全局偏移表)**。
  - **指令里写的是：** “去 GOT 表的第 3 项找变量地址”，而不是“去 0x1234 找变量”。
  - **加载时：** 操作系统只需要更新这个进程对应的 GOT 表，而不需要修改库的代码段。

## 延迟绑定与PLT表

为了提升启动速度，动态链接库通常采用“懒加载”策略。

- **原理**：如果一个程序链接了 100 个动态库函数，但运行时只用到了 1 个，那么启动时去解析 100 个地址是很浪费的。
- **机制**：**PLT (Procedure Linkage Table, 过程链接表)**。
  - 当你第一次调用动态库函数时，程序会跳转到 PLT 里的一个小段代码，这段代码会触发动态链接器去寻找真实地址并填入 GOT。
  - 第二次调用时，PLT 就会直接跳转到已经填好的真实地址，不再消耗寻找时间。

| **维度**       | **静态库 (.a / .lib)**                   | **动态库 (.so / .dll)**                       |
| -------------- | ---------------------------------------- | --------------------------------------------- |
| **部署便利性** | **极高**。单文件运行，无“缺少 DLL”报错。 | **一般**。需处理路径问题（LD_LIBRARY_PATH）。 |
| **内存与磁盘** | **浪费**。多份拷贝。                     | **高效**。内存中只有一份副本。                |
| **运行时性能** | **略高**。没有 PLT 跳转开销。            | **略低**。存在间接寻址开销。                  |
| **插件化架构** | **不支持**。                             | **支持**。可利用 `dlopen` 运行时动态加载。    |

# 符号表

符号表是在“编译阶段”开始创建，在“汇编阶段”最终固化到文件里的。而链接阶段则是“使用”和“合并”这些符号表。

**一、萌芽：编译阶段**

当编译器（`cc1`）在扫描你的翻译单元（TU）并构建 **AST（抽象语法树）** 时，它就已经在内存中维护一张查找表了。

- **目的**：为了进行“语义分析”。比如当你写 `x = 10;`，编译器需要查表看看 `x` 是不是已经定义过了？它的类型是 `int` 还是 `string`？
- **状态**：此时的符号表还在编译器的内存里，它记录了变量名、函数名、类型、作用域等信息。

**二、定型：汇编阶段**

这是符号表真正“落户”到磁盘上的时刻。汇编器（`as`）会将编译器传来的符号信息整理成固定格式，写入 `.o` 目标文件的 **`.symtab` 节 (Section)**。

此时的符号表包含了三类关键信息：

1. **已定义符号：本文件里定义的全局变量、函数。汇编器会给它们标上在 `.text` 或 `.data` 节中的**偏移量**。
2. **未定义符号：本文件里调用了、但没定义的（比如 `extern` 声明或 `printf`）。汇编器会给它们打上一个“待解决”的标记。
3. **局部符号**：带 `static` 关键字的变量或函数。它们被标记为 `LOCAL`，意味着**链接器在合并文件时会忽略它们**。

**三、消费与洗牌：链接阶段**

链接器（`ld`）不产生新的代码，它主要玩的就是“符号匹配游戏”。

- **符号解析**：链接器扫描所有 `.o` 文件的符号表。如果 `A.o` 有个未定义的 `foo`，它就在 `B.o`、`C.o` 的符号表里找谁拥有已定义的 `foo`。
- **符号合并**：链接器最后会把所有 `.o` 的符号表合并成一个巨大的、属于可执行文件的全局符号表（虽然为了减小程序体积，最终发布版通常会用 `strip` 命令删掉它）。

## 其它

**A. 强符号 vs 弱符号**

- **强符号**：函数名、已初始化的全局变量。
- **弱符号**：未初始化的全局变量（在某些环境下）。
- **规则**：链接器不允许两个同名的强符号（报错：Multiple Definition）；如果一个强一个弱，选强的；如果两个都弱，选占用空间大的。

**B. 符号修饰**

由于 C++ 支持重载，汇编阶段存入符号表的函数名并不是你在源码里写的 `void func(int)`，而是被修饰后的 `_Z4funci`。**链接器就是根据这个修饰后的名字进行精确匹配的。**

# 其它问题

## const全局变量的局部链接性

> 绝对不要在头文件中定义非内联函数或非 const 全局变量。因为一旦该头文件被多个 .cpp 包含，预处理后每个 .cpp 都会有一份该函数的代码，链接时必报“重定义”错误。

这及到 C++ 的**链接属性**：

**非 `const` 全局变量：外部链接**

默认情况下，全局变量（如 `int g_var = 10;`）是**外部链接**的。这意味着它的名字（符号）在整个工程中必须是唯一的，链接器会尝试在不同的 `.o` 文件间匹配这个名字。如果在两个 `.o` 里都找到了它，就会报错。

**`const` 全局变量：内部链接**

在 C++ 中，`const` 对象默认是**内部链接**的（类似于加了 `static`）。

- 当你在 `test.h` 里写 `const int MAX_VAL = 100;`。
- 每个包含它的 `.cpp` 文件在预处理后，都会在自己的翻译单元里拥有一份 `MAX_VAL` 的**独立拷贝**。
- **重点：** 链接器在链接时，看到这些 `const` 变量都被标记为“仅本单元可见”，所以它不会去尝试合并它们，也就不会产生冲突。

**注意：** 虽然 `const` 不报错，但如果变量占用内存较大（比如巨大的数组），在头文件里定义会导致每个 `.cpp` 都存一份拷贝，白白浪费二进制文件的体积。

## #ifdef的问题

**预处理器的视野：** 预处理器是以 `.cpp` 文件为单位工作的。每个 `.cpp` 文件（及其包含的所有头文件）被预处理后，会生成一个独立的 **翻译单元**。

**头文件卫士的作用：** `#ifndef` 只能保证在**同一个** `.cpp` 文件中，由于复杂的包含关系（比如 `A.h` 包含了 `B.h`，`main.cpp` 同时包含了 `A.h` 和 `B.h`）导致头文件内容被重复粘贴的问题。

如果你有 `main.cpp` 和 `tool.cpp`，它们都 `#include "test.h"`。

1. 预处理 `main.cpp` 时，由于它是独立翻译单元，`#ifndef` 检查通过，将函数定义拷入。
2. 预处理 `tool.cpp` 时，它也是独立翻译单元，**它完全不知道 `main.cpp` 预处理了什么**，所以 `#ifndef` 再次检查通过，也将函数定义拷入。
3. **编译阶段：** 两个 `.cpp` 都变成了各自的 `.o`（或 `.obj`）目标文件。每个目标文件的符号表里都有一个同名的“强符号”函数。
4. **链接阶段：** 链接器把这两个 `.o` 往一块儿凑，发现：“嘿！怎么有两个叫 `foo()` 的函数定义？”——**LNK2005 重定义错误爆发**。

**结论：** 头文件卫士防的是“单文件内重复包含”，防不住“多文件间定义冲突”。

> 如果架构需要让多个文件共享某些东西，正确的做法有：

**A. 全局变量：extern 声明 + cpp 定义**

- **test.h**: `extern int g_count;`（这只是告诉编译器：有个变量叫这个名字，别处定义的）
- **test.cpp**: `int g_count = 0;`（真正的内存分配，全工程只此一份）

**B. 函数：inline 关键字**

- **test.h**: `inline void func() { ... }`
- **原理：** `inline` 告诉链接器：“如果在这个工程里看到多个同名定义，没关系，它们都是一样的，你随便挑一个用，或者直接把它们内联掉。” 这样就不会报重定义错误了。

**C. 现代 C++ 方案：inline 变量 (C++17)**

从 C++17 开始，你可以直接在头文件写：

- `inline int g_var = 10;` 它像 `inline` 函数一样，允许在多个编译单元存在，但链接后最终只保留一个实例。这是目前做 **Header-only 库** 最推荐的做法。

## 为什么.o不能直接运行

**问：为什么 `.o` 文件不能直接运行？** **答：** 因为 `.o` 文件只是一个局部模块。虽然它包含了机器码，但它不知道外部库函数的具体内存地址（重定位问题），也没有操作系统要求的完整文件头信息（如程序的入口地址 `_start`）。

## 只改动一个文件

**问：如果我只改动了一个 `.cpp`，整个图里的步骤都要重跑吗？** **答：** 不需要。这就是 **“增量编译”**。只有被修改的 `.cpp` 需要重新经历预处理、编译和汇编生成新的 `.o`。最后，链接器将新的 `.o` 和其他没变动的 `.o` 重新链接即可。这大大节省了大型项目的开发时间。

## 如果两个 `.cpp` 都包含了同一个头文件，代码会被复制两次吗？

如果两个 `.cpp` 都包含了同一个头文件，代码会被复制两次吗？

取决于你写的是“**声明**”还是“**定义**”。

**情况 A：头文件里只有声明（最常见的架构）**

- **过程**：`main.cpp` 和 `tools.cpp` 都包含了 `math.h`（里面只有 `void func();`）。
- **结果**：预处理后，每个 `.cpp` 都知道有这个函数，但都没代码。静态链接时，链接器从库里找到 `func` 的**唯一一份代码**，让两个 `.cpp` 都指向它。
- **结论**：**没有副本**。

**情况 B：头文件里写了定义（这就是你怀疑的“副本”）**

如果你违反了规矩，在头文件里写了 `void func() { ... }`（且没加 `inline`）：

1. **预处理**：`main.i` 有一份 `func` 代码，`tools.i` 也有一份。
2. **编译**：`main.o` 里有一块二进制代码叫 `func`，`tools.o` 里也有。
3. **链接**：链接器尝试合并。它发现两个 `.o` 都有 `func` 的强符号。
4. **报错**：`Multiple definition of func`。
5. **结论**：**链接器不允许这种“副本”存在，它会报错把你拦下来。**

## 为什么静态库看起来像在“复制”？

你提到的“包含了几次就复制几次副本”，其实是指**不同程序之间**，而不是同一个程序内部。

- **程序 X** 静态链接了 `libA.a`。
- **程序 Y** 也静态链接了 `libA.a`。
- **结果**：在硬盘和内存里，确实有**两份完全相同的代码副本**。一份死死地焊在 `X.exe` 里，一份焊在 `Y.exe` 里。它们互不关联。

## 两个静态库有同名全局变量

这个问题的“标准答案”取决于这两个变量的**符号属性**（强 vs 弱）。

**情况 A：两个都是“强符号”（最常见）**

如果你在两个静态库里都写了 `int g_val = 10;`（已初始化的全局变量是强符号）：

- **结果**：**链接报错（Multiple Definition / LNK2005）**。
- **原因**：链接器发现两个完全一样的“重担”，它不知道该信任哪一个，为了保证程序的唯一性和安全性，它选择罢工并报错。

**情况 B：一个强，一个弱**

如果一个是 `int g_val = 10;`，另一个是 `int g_val;`（未初始化的全局变量在 C 语言中常被视为弱符号，但在现代 C++ 中通常也视为强符号，除非使用了特殊属性）：

- **结果**：**链接通过，取强符号的值**。
- **逻辑**：链接器认为有具体定义的（强）比模糊的（弱）更可靠。

**情况 C：都是“弱符号”**

- **结果**：**链接通过，选择内存占用较大的那一个**。

## 两个三方库都冲突了怎么办

例如都有`void initialize()`

**动态链接替代**：将其中一个库改为动态链接（`.so` / `.dll`）。动态链接库有自己的符号空间，可以利用 `dlopen/dlsym` 或不同的命名空间避开冲突。

## 头文件的函数在cpp中没有实现会报错吗 

**如果你没调用它**：**不报错**。编译器在编译阶段只看声明，既然你没用它，链接器也就不需要去寻找它的地址，整个过程平安无事。

**如果你调用了它**：**链接阶段报错**（`undefined reference to...`）。编译器在编译时会通过（它相信你会在别处实现），但链接器在最后“填坑”时发现找不到该函数的机器码地址，于是报错。

## 为什么类的定义可以放在头文件里而不报“重定义”？

类定义（数据成员和成员函数声明）本质上是一张“图纸”，它不直接占用内存（不产生强符号）。

只要每个翻译单元看到的类定义是**完全一致**的，就不违反 **ODR（单一定义规则）**。

**注意**：如果类成员函数在类体内部直接实现，它会被自动视为 `inline`，链接器会负责合并。

## 为什么全局变量声明在 `.h` 里，必须加 `extern`？

`int g_val;` 是**定义**（分配内存，产生强符号）。如果多个 `.cpp` 包含它，链接时会报重定义错误。

`extern int g_val;` 是**声明**（告诉编译器：符号在别处）。它不分配内存，不产生强符号，所以包含多少次都没问题。

## 结构体的内存对齐是在哪个阶段确定的？

编译器在将 C++ 翻译成机器指令时，必须知道每个成员相对于结构体首地址的**偏移量（Offset）**。

为了硬件访问效率，编译器会自动插入填充字节（Padding）。这意味着在 `.o` 文件生成时，对象的内存布局就已经“死”了。

## 如果一个函数被标记为 `static`，它在链接阶段有什么特殊待遇？

 它变成了**内部链接**。

- 汇编阶段生成的符号表中，该函数会被标记为 `LOCAL`。
- 链接器在合并多个 `.o` 文件时，**完全看不见**这些 `LOCAL` 符号。
- **架构意义**：即使两个 `.cpp` 里都有同名的 `static void func()`，它们也互不干扰，链接器不会报冲突。这是实现“文件级封装”的重要手段。

## 我在 `A.h` 里写了 `const int count = 10;`，然后在 `main.cpp` 和 `test.cpp` 里都包含了它。请问最终的可执行文件里有几份 `count`？

当 `main.cpp` 和 `test.cpp` 都包含了 `A.h`，预处理器会在两个翻译单元里各放入一个 `const int count = 10;`。

**编译器的处理**：编译器处理 `main.cpp` 时，看到的是一个只属于 `main.cpp` 的 `count`；处理 `test.cpp` 时，看到的是另一个独立的 `count`。

**链接器的行为**：因为它们是内部链接，链接器**不会**把它们合并成一个。

**情况 A：被编译器“优化掉了”（最常见）**

由于 `count` 是一个字面量常量（10），编译器在编译阶段通常会直接进行**常量折叠**。

- 编译器直接把代码里的 `count` 替换成了数字 `10`。
- 在这种情况下，最终的可执行文件里**一份 `count` 都没有**，它只存在于机器指令的立即数中。

**情况 B：被强制分配了内存**

如果你在代码里做了某些操作，迫使编译器必须给 `count` 分配地址，比如：

- 拿了它的地址：`const int* p = &count;`
- 或者它是一个复杂的对象（如 `const std::string`）。 由于是内部链接且无法合并，`main.o` 和 `test.o` 会**各自**在自己的只读数据段（`.rodata`）里分配 4 个字节。
- **结果**：最终的可执行文件里会有 **2 份** 物理地址不同的 `count`。

## 在头文件中定义了一个非内联函数（非静态），并将其包含在两个不同的 .cpp 文件中。请问在编译阶段和链接阶段分别会发生什么？

假设你在 `tools.h` 中定义了：`void func() { /* 代码体 */ }`（既没加 `inline`，也没加 `static`）。 然后 `A.cpp` 和 `B.cpp` 都 `#include "tools.h"`。

**编译阶段：平安无事**

- **发生了什么**：预处理器把 `func` 的代码分别拷贝进了 `A.i` 和 `B.i`。
- **编译器视角**：
  - 编译 `A.cpp` 时，看到一个 `func` 定义，没问题，生成机器码，存入 `A.o`。
  - 编译 `B.cpp` 时，看到一个 `func` 定义，没问题，生成机器码，存入 `B.o`。
- **符号表状态**：`A.o` 和 `B.o` 的符号表里都赫然写着：**`func` (全局/强符号)**。
- **结果**：编译器愉快地完成了任务，并不知道灾难即将来临。

**链接阶段：爆发冲突**

- **发生了什么**：链接器（`ld`）试图把 `A.o` 和 `B.o` 融合成一个可执行文件。
- **链接器发现**：它在 `A.o` 里找到了 `func`，又在 `B.o` 里找到了同名的 `func`。
- **它的逻辑**：因为这不是 `inline` 符号，它们都是**“强符号”**。链接器无法判断这两个 `func` 是不是同一个东西（万一逻辑不一样呢？），它不敢擅自合并。
- **结果**：抛出致命错误：**`fatal error LNK1169: 找到一个或多个重定义符号`**（或 `multiple definition of 'func'`）。

## 在头文件中定义函数的四种方案

架构设计上有四种主流方案，根据你的需求（性能、封装、还是库设计）来选择：

**方案 A：使用 `inline` 关键字（最推荐）**

```c++
// tools.h
inline void func() { ... }
```

- **原理**：告诉链接器，“如果看到多个同名定义，它们是一样的，请合并成一个”。
- **适用**：短小的函数、Header-only 库。

**方案 B：只在头文件声明，在 `.cpp` 实现（最标准）**

```c++
// tools.h
void func(); // 只有声明

// tools.cpp
void func() { ... } // 真正的定义
```

- **原理**：全工程只有 `tools.o` 里有一份 `func` 代码。其他文件（如 `A.o`）只留个地址坑位。
- **适用**：绝大多数常规工程，能加快编译速度（修改 `.cpp` 不需要重新编译包含它的文件）。

**方案 C：使用 `static` 关键字**

```c++
// tools.h
static void func() { ... }
```

- **原理**：让 `func` 变成“文件私有”。`A.o` 有一份 `A_func`，`B.o` 有一份 `B_func`，它们互不干扰。
- **缺点**：如果 100 个文件包含了它，你的程序里就有 100 份一模一样的代码副本，**浪费空间**。

**方案 D：放入类定义内部**

```c++
// tools.h
class Tool {
public:
    void func() { ... } // 类内部实现的函数默认为 inline
};
```

- **原理**：C++ 规定在 `class` 内部直接写的成员函数，默认自带 `inline` 属性。

| **方案**         | **链接属性**      | **最终副本数**      | **链接报错？** |
| ---------------- | ----------------- | ------------------- | -------------- |
| **直接定义**     | 外部链接 (强符号) | 无法合并            | **报错**       |
| **`inline`**     | 外部链接 (弱符号) | **1 份** (自动去重) | 不报错         |
| **`static`**     | 内部链接          | **每个文件 1 份**   | 不报错         |
| **声明+CPP实现** | 外部链接 (强符号) | **1 份**            | 不报错         |

# 关于inline的弱定义

**编译阶段**：当编译器在 `main.cpp` 和 `tools.cpp` 中都看到 `inline void func() {...}` 时，它会正常生成该函数的机器码。

**符号表标记**：汇编器会将这个符号标记为 **“弱”**或者特殊的**“Linkonce”**属性。

**链接阶段**：链接器发现有两个（或多个）叫 `func` 的定义。

- 如果是普通函数，链接器会报错“重定义”。
- 如果是 `inline` 函数，链接器会认为：**“既然作者说了是 inline，那我就假设这些定义的内容都是一模一样的。为了节省空间，我只保留其中一个的机器码，把其他的通通删掉，并将所有的调用点都指向保留下来的那一份。”**

## 一个 `inline` 可以用在多个头文件吗？

**可以，但通常不建议这么做。** 正确的做法是：**定义在同一个头文件中，被多个 `.cpp` 包含。**

我们要区分两种“重复”：

**情况 A：同一个头文件里的 `inline` 被多次 `#include`（标准做法）**

- `math.h` 里写了 `inline int add(int a, int b) { return a + b; }`。
- `A.cpp` 和 `B.cpp` 都包含了 `math.h`。
- **结果**：完全合法。链接器会合并它们。这是 `inline` 设计的初衷，也是解决“头文件定义函数”报错的唯一方案。

**情况 B：在不同的头文件里写了同名的 `inline`（危险动作）**

- `math_v1.h` 里有 `inline void print() { cout << "V1"; }`
- `math_v2.h` 里有 `inline void print() { cout << "V2"; }`
- 如果你的工程里有的文件包了 V1，有的包了 V2，最后链接在一起。
- **结果**：**未定义行为**。链接器会随机挑一个（可能是 V1，也可能是 V2）。你的程序可能会在某些地方表现正常，某些地方逻辑诡异，且编译器**完全不会报错**。

**inline是全局唯一的，不能说在v1中inline一个print()，在v2中inline一个和print()**

因为这违反了单定义规则

## 如果想要真正的局部性

**方案 A：使用匿名命名空间——推荐**

这是现代 C++ 替代 `static` 的标准做法。

```c++
// 在 A.cpp 中
namespace {
    void func() { /* V1 逻辑 */ }
}

// 在 B.cpp 中
namespace {
    void func() { /* V2 逻辑 */ }
}
```

- **效果**：编译器会给这两个 `func` 生成极其复杂的、唯一的内部名字。它们在链接阶段是**不可见**的，因此绝对不会冲突。

**方案 B：使用 `static` 关键字**

```c++
// 在头文件里
static void func() { ... }
```

- **效果**：每个包含该头文件的 `.cpp` 都会拥有一份该函数的**私有拷贝**。
- **副作用**：这会增加二进制文件的体积，因为链接器不会合并它们。所以除非必要，否则不要在头文件里写 `static` 函数。

# 虚函数表与内联

## 虚函数表的存储位置

vtable 本质上是类相关的只读数据（`.rodata`）。链接器的任务是确保：

- 即使多个 `.cpp` 都包含了这个类的头文件，最终的可执行文件中**每个类只有一份 vtable**。
- **优化策略**：为了避免重复，编译器通常会把 vtable 放在包含“第一个非内联、非纯虚函数成员”定义的那个 `.obj` 文件中。

处理 `inline virtual` 函数

## 虚函数可以是 inline 的吗？

- **答案是：可以，但只有在特定情况下才会真的内联。**
- **链接器的角色**：如果你在类定义中直接实现了虚函数，它被视为 `inline`。
  - 如果你通过对象直接调用（如 `obj.func()`），编译器能确定类型，就会在编译/链接阶段直接**内联展开**。
  - 如果你通过指针调用（多态），链接器必须提供一个**真实的函数地址**放入 vtable。此时，`inline` 标记只起到“允许重复定义并合并”的作用，函数体本身不会被内联。
